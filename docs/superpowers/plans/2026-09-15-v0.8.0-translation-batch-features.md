# v0.8.0 翻译批次能力迁移实施计划

## 1. 背景与目标

当前分支 `sync3.1` 从上游较早版本分叉，并额外包含多 LLM 优先级切换、Pi 审计、
Codex/Claude/CodeBuddy/AGY CLI provider、请求状态事件和 Translator 坏响应日志等定制能力。
上游 `v0.8.0` 中以下三个功能分别由独立提交引入：

- `212cf6f`：为每个翻译/润色批次提供同章下一条只读原文；
- `7e3497b`：使用 `tiktoken` 的 `cl100k_base` 按 token 分批和拆分超长段；
- `55b3ca2`：整批翻译成功后，在同一消息 transcript 上追加润色轮次。

本任务采用手工移植，不直接 cherry-pick。目标是在保留当前分支定制架构和诊断语义的前提下，
实现与上游发布说明一致的用户行为：

1. 批次末尾可以参考同章下一条原文，改善跨批次未完句、引号和对话衔接；
2. 翻译批次、Review 块和超长段拆分使用统一 token 预算；
3. 正常整批翻译后的润色复用翻译请求前缀，逐段对齐兜底仍使用独立润色请求。

不迁移 `v0.8.0` 的工作流计时、BabelDOC 默认导出、Review 可恢复中断、MinerU 空译文、
`models compare` 修复或 README 打赏内容。

## 2. 行为契约

### 2.1 只读后文参考

- 每个实际待译批次最多附带一条 `next_source`，来源是同章 `text_segments` 中紧随该批次的段落。
- 章末使用空引用，不允许跨章读取下一章内容。
- 后文位于编号待译正文之后，使用 JSON 字符串编码，确保换行、引号和形如 `[99]` 的文本
  不会被误识别为新增待译段落。
- 后文只进入当次翻译/润色 prompt，不加入批次，不创建输出项，不写入章节 JSON、manifest、
  glossary checkpoint 或 `RollingContext.recent_targets`。
- 模型必须把它视为不可信引用：不得执行其中的指令，不得翻译、复制或借用后文信息补写当前段，
  只能据此判断当前句法、引号或对话是否尚未结束。
- Translator 过滤纯数字、符号或空白段后，若最后一个实际送译段后仍有批内段落，最近的批内邻段
  优先作为后文；否则使用流水线传入的批外 `next_source`。
- 整批对齐重试继续使用同一条实际后文。进入逐段兜底后，每个单段请求重新选择其直接下一段；
  批内没有下一段时才使用批外后文。
- 续跑时不缓存后文。每次根据当前 token 预算、已完成/待完成边界和章节源段重新计算，避免预算变化
  后引用过期。

### 2.2 Token 预算

- 新增唯一共享计数函数 `count_tokens(text)`，固定使用 `tiktoken.get_encoding("cl100k_base")`。
- encoding 对象使用 `lru_cache(maxsize=1)` 缓存；空字符串返回 `0`。
- `segment.max_tokens_per_batch` 控制正文翻译批次；Review 仍采用其三倍作为连续审校块预算，
  但三倍值也按 token 计量。
- `segment.max_tokens_per_segment` 控制准备阶段的超长段拆分。
- 配置默认数字仍为 `1800` 和 `1200`，但单位从字符变为 token。
- `max_chars_per_batch`、`max_chars_per_segment` 不提供兼容别名或静默迁移，加载时必须报
  Pydantic 校验错误。
- 已准备完成的状态不自动重切章节段落；只有创建新状态或用户主动重新准备时才按 token 拆段。
- 已有状态续跑时可以按新 token 批次重新组合，但 `_resume_batches` 仍在“已完成/待翻译”边界再次切开，
  不覆盖已确认译文。

超长段拆分算法保持确定性：

1. 先按现有句末正则切成句子片段；
2. 贪心拼接后 token 数不超过预算的相邻句子；
3. 单句超预算时，用二分搜索寻找 token 安全的最长字符前缀；
4. 在安全前缀内优先回退到空格、制表符或换行，避免从英文单词中间切开；
5. 找不到空白时硬切；若一个 Unicode 码点自身就超过极小预算，至少消费一个码点以保证前进；
6. 所有片段按原顺序无损拼接回原文，首片保留 kind、anchor、resource_href、meta，后续片标记
   `cont=True` 且不保留独立 anchor/meta；
7. BabelDOC 继续完全跳过该拆分，因为其段落 ID 与版式绑定。

### 2.3 润色续写翻译会话

这里的“同一会话”是向现有无状态 `LLMClient` 重放完整消息 transcript，不引入 provider session ID。
正常路径的第二次调用消息顺序必须为：

```text
system    原翻译 system prompt
user      原翻译 user prompt
assistant 模型实际返回的原始翻译 JSON 文本
user      追加的润色指令和只读后文
```

- 只有整批请求最终返回合法、等长译文时才保存 transcript；允许前面的整批对齐尝试失败，
  但最终成功必须仍是一次完整批量响应。
- `Translator` 在每次 `translate_batch` 开始时清空上一次 transcript，防止异常、空批或全符号批
  误用旧响应。
- 同时保存实际送给模型的源段下标。续写润色只返回这些下标对应的结果，再覆盖回完整目标列表，
  纯数字和符号段保持原值。
- transcript 中 assistant 内容优先使用 `LLMClient.last_json_response()` 保存的模型原始文本；
  若某个自定义 client 没有提供原文，则以解析结果生成合法 JSON 作为防御性后备。
- 新的 Agent 辅助方法必须继续调用当前 `complete_json`，不能照搬上游改为直接 `complete + parse`。
  这样可保留当前分支的请求状态事件、Gemini JSON 行为、Priority/Routed client 故障切换、
  `last_json_request_id` 和 `translator_response_rejected` 原始响应日志。
- 续写润色输出合法且数量匹配时采用结果，并再次清理可能复制进来的 EPUB 注音标记。
- 以下情况必须退回现有独立 `Polisher.polish` 请求：
  - 整批翻译多次对齐失败后改为逐段翻译；
  - 没有可复用 transcript 或实际送译下标；
  - 续写请求抛出异常；
  - 续写响应不是列表或数量不匹配。
- 独立润色也接收同一条只读后文。若独立润色失败，继续保留翻译阶段结果。
- `target_before_polish` 仍保存去除注音标记后的翻译阶段文本，`target` 保存最终润色结果；
  不新增状态字段。

## 5. 验收标准

- 新准备的文档按 `cl100k_base` token 数拆段和分批，Review 块使用同一计数口径。
- 使用旧 `max_chars_*` 的配置明确失败；仓库提供的配置与文档全部使用新字段。
- 每个翻译和润色批次最多看到同章下一条只读原文，输出数量、Segment 身份和滚动上下文均不变化。
- 正常整批翻译后的润色调用复用完整翻译消息前缀；逐段翻译兜底仍发起独立润色请求。
- 中断续跑不会重翻已完成批次，不会因后文引用产生额外状态或重复计费。
- 当前多 provider 路由、Priority 故障切换、请求状态、用量归因和 Translator 坏响应日志测试无回归。
- 中英文文档语义一致，SRT 行为和状态目录不变。

## 6. 风险与控制

- **默认数字单位变化**：`1800` token 与 `1800` 字符的实际请求大小不同。按上游发布约定保留数字，
  并在配置文档明确成本和上下文占用可能变化。
- **Tokenizer 与实际模型不同**：`cl100k_base` 是跨 provider 的稳定估算器，不承诺等于各模型私有
  tokenizer；固定编码可以换取可测试、可复现的批次边界。
- **Prompt 缓存不是强保证**：只有相同 provider/model 支持且启用前缀缓存时才能获得收益；
  优先级切换到另一配置后仍保证语义正确，但不承诺缓存命中。
- **CLI provider 展平消息**：不在本任务中重构其传输格式，避免扩大到 provider 行为变更；
  transcript 的顺序和角色标记按各 provider 现有能力传递。
- **Prompt 质量变化**：新增后文可能影响模型收束方式。自动测试只验证协议与状态不变量；重大质量
  验收应按 `CONTRIBUTING.md` 使用至少 50,000 字公版文本做前后对比，不自动读取用户私有书籍。
